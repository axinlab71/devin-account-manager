# Devin Desktop「模型列表不显示」问题诊断报告

> **归档性质：调查材料。** 本报告是对一次真实故障的只读调查记录与根因分析，其中根因声明与测试结论来自调查当时的本机环境；管理器内的「模型列表诊断与恢复」功能以本报告为参考独立实现，不把本报告结论当作已证实的产品行为。
>
> 调查对象：Devin Desktop 1.126.0（本机安装路径已省略）＋ Devin Account Manager
> 日期：2026-10-17 ｜ 性质：只读调查 + 管理器新增诊断功能，未改动任何官方客户端文件

---

## 一句话结论

**模型列表空白的直接原因：本地 agent（devin.exe）向 codeium.com（Google Cloud）认证超时失败（10 秒硬超时），与代理软件共存环境放大了网络波动。云端 agent 走另一条更稳的线路（AWS CloudFront），所以"切云端就好"。软件本身没坏，坏的是网络环境的可预期性。**

---

## 一、问题机理（已从官方客户端源码逆向确认）

```
Devin.exe (Electron IDE)
  └─ 内置 windsurf 扩展 ──ACP(stdio)──> devin.exe (Rust agent)
                                          │
                                          ├─ 认证: server.codeium.com 拉 team settings ← 10秒超时, 失败即硬失败
                                          ├─ 配置: unleash.codeium.com                 ← 2/5/10秒, 有降级缓存
                                          ├─ 推理: inference.codeium.com               ← 对话时每次调用
                                          │
                                          └─ 认证成功才会上报模型列表(ACP configOptions)
                                             └── 认证失败 → 模型下拉框空白 → "None selected"

云端 agent (devin-cloud)：不跑本地进程, 一条 wss 长连接到 app.devin.ai (CloudFront)
                         模型和推理全在 Cognition 服务器 → 对本地网络质量几乎无感
```

**为什么"有时好有时坏"**：当时对 codeium.com 的多次网络测试显示明显丢包和较大延迟波动；agent 每次启动需要多次网络请求，任一认证请求超过客户端超时就可能导致启动失败。重启可能改变当次网络请求结果，因此有时看起来有效。

**为什么"多梯子软件更容易炸"**（四个机制叠加）：

1. **系统代理单槽位漂移**：Windows 系统代理只有一份，多个梯子互写端口，指向已退出软件的端口 → 请求黑洞 → 超时。
2. **PAC 残留**：调查时发现系统中有未启用的 PAC 配置残留。Electron 与 Rust 网络组件对系统代理/PAC 的处理可能不同，界面和 agent 的实际网络路径需要分别验证。
3. **TUN 互抢**：两个开 TUN 的梯子各装虚拟网卡抢路由，流量被静默丢弃 → 挂起到超时。
4. **子进程配置冻结**：devin.exe 是长驻进程，启动时的网络环境被冻结；切梯子后必须重启 Devin（任务管理器确认 devin.exe 也结束）才生效。

## 三、已排除 / 未排除

- ✅ **已排除**：切号器是根因（纯官方退出/网页登录同样复现）、扩展文件损坏、渲染类问题、代理完全失效。
- ❓ **未排除**：个别账号的 team settings/套餐差异（需下次故障时按账号对比采集）、"请求成功但响应为空"分支（需故障窗口抓证据）、偶发 DNS 污染会话。

## 四、给顾客的处置建议（按顺序）

1. **首选长期方案**：网络不稳的顾客直接把默认 agent 设为云端（`devin.acp.preferredAgent: "devin-cloud"`），本地作备用。
2. **本地模式要用得稳**：一机只留一个梯子；切换梯子后彻底重启 Devin（含 devin.exe 子进程）。
3. **修复代理配置**：如确实需要代理，在 Devin 设置中填写本机代理软件当前正在使用的地址和端口；不要照抄其他设备的端口。该设置键为顶层 `"http.proxy"`。
4. **清残留 PAC**：`inetcpl.cpl` → 连接 → 局域网设置 → 取消"使用自动配置脚本"。
5. **故障时**：先点"重新诊断"，再按结论操作；重启类操作前先保存工作。

## 五、管理器相关功能（实现状态以当前源码和交接文档为准）

**位置**：左侧导航 → **诊断与恢复**

- **开始诊断**：一键执行 4 组只读检查（客户端环境/进程、代理四角对照、4 域名 TCP+TLS 计时、agent 日志聚合），每项输出三态：**已确认异常 / 检查正常 / 无法判断**（不会无依据地报"正常"）。
- **查看脱敏结果 / 导出脱敏报告**：报告只存本机（`%LOCALAPPDATA%\DevinSwitcher\diagnostics\`），自动脱敏 token/邮箱/密钥/URL secret/用户名，可安全发回。
- **按结论提供恢复操作**（需逐项确认，无"一键全清"）：
  - 写入客户端代理设置（原子备份 settings.json，只改 http.proxy）
  - PAC 清除指引（仅手动步骤说明，不改注册表）
  - 温和重启官方客户端（需勾选"已保存工作"）

**验证状态**：本报告所述验证属于调查当时的本机结果；当前实现及测试状态请以仓库中的交接文档为准。公开版省略了本机路径、端口、PID 和具体网络指标。

**待人工验证**：① 官方退出→网页重登全流程；② 真实故障时执行恢复操作后，以"模型列表真正显示、选模型发消息正常"为最终验收。

## 六、下次故障的排查话术（30 秒版）

> "你的网络到 Devin 本地服务器是直连通的，但这条国际线路丢包高、延迟忽快忽慢（1 秒到 8 秒以上）。本地模式要求 10 秒内完成认证，赶上抖动就失败、模型列表空白；云端走的是另一条更近更稳的线路，所以切云端就好。不是软件坏了，是网络质量在及格线附近波动。打开管理器 → 设置 → 客户端 → 连接诊断与修复，点开始诊断，把脱敏报告发我。"
